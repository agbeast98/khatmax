# 13 - Release

Release در Khatmax فقط انتشار نسخه نیست؛ لحظه‌ای است که باید مطمئن شویم محصول، پایدار، قابل‌اعتماد و آماده‌ی استفاده است. چون پروژه AI-first است، release باید هم کیفیت فنی را بسنجد و هم کیفیت تجربه‌ی AI را.

## هدف
- اطمینان از پایداری نسخه
- کاهش regression
- حفظ هماهنگی بین core، AI و runtime
- آماده‌سازی محصول برای استفاده‌ی واقعی

## release checklist
- build باید سالم باشد.
- تغییرات مهم باید review شده باشند.
- behaviorهای حساس باید بررسی شوند.
- docs و metadata باید هم‌راستا باشند.
- providerها و integrationها باید بررسی شوند.

## چیزهایی که باید چک شوند
- سازگاری با `Code - OSS` / `VS Code`
- رفتار workspace
- agent flow
- live runtime
- browser preview
- auth و backend
- performance و stability

## versioning
- نسخه باید واضح باشد.
- تغییرات major باید قابل‌ردگیری باشند.
- اگر API یا architecture تغییر کرده، باید در release notes دیده شود.
- release باید تاریخچه‌ی قابل‌فهم داشته باشد.

## rollout
- تغییرات حساس بهتر است مرحله‌ای منتشر شوند.
- اگر feature جدید روی هسته اثر دارد، باید با احتیاط منتشر شود.
- monitoring بعد از release مهم است.
- feedback باید به roadmap برگردد.

## کیفیت release
- نسخه باید بدون شکستن جریان اصلی کار کند.
- AI باید در release قابل‌اعتماد باشد.
- کاربر باید بتواند control و visibility لازم را داشته باشد.
- اگر feature ناقص است، باید شفاف اعلام شود.

## مسیر بلندمدت
- release برای desktop، cloud و enterprise می‌تواند تفاوت داشته باشد.
- نسخه‌های آینده باید هم محصولی و هم فنی به‌روز شوند.
- هر release باید زمینه‌ساز رشد بعدی باشد.

## نتیجه‌ی مطلوب
- نسخه‌ی پایدار
- خروجی قابل‌اعتماد
- آماده برای کاربر واقعی
- قابل‌گسترش برای releaseهای بعدی
