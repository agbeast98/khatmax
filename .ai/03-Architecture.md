# 03 - Architecture

Khatmax بر پایه‌ی `Code - OSS` و سازگاری با `microsoft/vscode` ساخته می‌شود، اما معماری نهایی آن باید برای یک AI Workspace مستقل و توسعه‌پذیر طراحی شود. هدف معماری، فقط سازمان‌دهی کد نیست؛ هدف ساختن یک سیستم قابل‌گسترش برای AI، workspace، runtime و collaboration است.

## اصل معماری
- هسته‌ی فعلی باید با ساختار VS Code سازگار بماند.
- لایه‌های Khatmax باید به‌صورت ماژولار اضافه شوند.
- مرز بین UI، service، agent و backend باید روشن باشد.
- هر بخش باید بتواند مستقل رشد کند، بدون اینکه کل سیستم را شکننده کند.

## لایه‌های کلیدی
- `Desktop Application`: اپ اصلی که کاربر با آن کار می‌کند.
- `AI Workspace`: لایه‌ی تجربه‌ی مرکزی برای کار با پروژه و AI.
- `Agent Engine`: موتور اجرای وظایف هوش مصنوعی.
- `AI Server`: سرویس‌های مرکزی برای orchestration و مدیریت درخواست‌ها.
- `Model Gateway`: لایه‌ی اتصال به providerها و مدل‌های مختلف.
- `Workspace Sync`: هماهنگ‌سازی state، فایل‌ها و context.
- `Live Runtime`: مشاهده و تحلیل اجرای واقعی پروژه.
- `Live Browser`: مشاهده‌ی زنده‌ی اپلیکیشن در مرورگر.
- `Deployment Service`: مدیریت استقرار و publish.
- `Monitoring`: رصد وضعیت، خطا و رفتار سیستم.

## جریان داده
- کاربر در `AI Workspace` یک درخواست می‌دهد.
- درخواست به `Agent Engine` و سپس به `AI Server` می‌رسد.
- `Model Gateway` مدل مناسب را انتخاب یا route می‌کند.
- خروجی به workspace برمی‌گردد و در صورت نیاز روی runtime یا browser اثر می‌گذارد.
- نتیجه باید برای کاربر قابل‌مشاهده، قابل‌فهم و قابل‌توقف باشد.

## نقش VS Code در معماری
- `Code - OSS` هسته‌ی اصلی تجربه و سازگاری است.
- Khatmax روی همین هسته، لایه‌های جدید می‌سازد.
- معماری جدید نباید پایه‌ی VS Code را دور بزند، بلکه باید آن را گسترش دهد.
- هر تغییری که به core نزدیک است باید با دقت بیشتر انجام شود.

## AI-first architecture
- سیستم باید برای همکاری با چند agent طراحی شود.
- تصمیم‌ها باید قابل‌نمایش و قابل‌ردگیری باشند.
- مسیر تصمیم‌گیری AI باید تا حد ممکن روشن باشد.
- کاربر باید بتواند بین اجرا، توقف، اصلاح و بازپخش جابه‌جا شود.

## ماژولار بودن
- هر capability باید مرز روشن داشته باشد.
- ماژول‌ها باید قابل‌جایگزینی و قابل‌توسعه باشند.
- افزودن feature جدید نباید باعث پیچیدگی غیرضروری در core شود.
- تغییر در یک لایه باید اثرش روی لایه‌های دیگر قابل‌تحلیل باشد.

## پشتیبانی از مدل‌ها
- معماری نباید به یک مدل خاص وابسته باشد.
- باید از cloud model و local model پشتیبانی کند.
- Providerهای جدید باید بدون بازنویسی کامل سیستم قابل‌اتصال باشند.
- routing مدل‌ها باید در `Model Gateway` یا لایه‌ی مشابه کنترل شود.

## سطوح اجرا
- Desktop اولویت اصلی محصول است.
- Web و cloud باید در ادامه قابل‌پشتیبانی باشند.
- Local runtime برای توسعه و کنترل بیشتر اهمیت دارد.
- Browser runtime برای preview و validation مهم است.

## اصولی که معماری باید حفظ کند
- شفافیت
- توسعه‌پذیری
- سازگاری با VS Code
- کنترل‌پذیری AI
- عملکرد مناسب
- قابلیت نگهداری

## نتیجه‌ی معماری مطلوب
- سیستم باید برای رشد بلندمدت آماده باشد.
- باید بتوان اجزای مختلف را مستقل توسعه داد.
- باید بتوان AI، runtime و deployment را در یک flow منسجم نگه داشت.
- باید هم برای محصول فعلی و هم برای نسخه‌های آینده قابل‌اتکا باشد.
